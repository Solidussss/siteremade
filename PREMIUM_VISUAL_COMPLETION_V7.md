## 1. Why OpenAI cost was ~$0.00 on a photo-led real-estate site (Part 2 — traced, not guessed)
Two independent, compounding bugs, both in code that was already live on `main`:

1. **`realestate` was never treated as photo-led.** `familyFor()` mapped `categoryKey === 'realestate'` into the generic **`professional`** family (same bucket as lawyers/accountants), and V6's `isPhotoLed()` only turns a `professional`-family business photo-led when the description uses personal-brand wording ("I help…", "coach", "independent"). A plain **team** description ("Residential real estate team…") never matches, so the entire V6 photo-led machinery — shot lists, minimum photo counts, the editorial page plan, the photo-set acceptance gate — never engaged for real estate. Traced in `lib/premium/grounding.js` (`familyFor`) and `lib/premium/editorial.js` (`isPhotoLed`).
2. **The `professional`→`consultancy` visual profile allows a text-only hero.** `PROFILES.consultancy.heroVariants` includes `'poster'`, which is one of the three `TEXT_ONLY_HERO_VARIANTS` — `renderHero` never calls `renderVisualSlot` for a text-only layout, so **no hero image slot is even planned**. Combined with the default `trust-heavy-professional` section hierarchy (`['home','services','about','faq','contact']`, no gallery/imageLedEditorial section by default), a real-estate site whose creative-direction heuristic happened to land on `poster` (or `minimal-text-only`/`centered-oversized`) ends up with **zero image-bearing sections anywhere on the site** — not a budget/credit decision, a planning decision. That fully explains Claude ≈ $0.12 (planner + one critic call) and OpenAI = $0.00.
3. Ruled out: credits, provider configuration, and the budget governor — none of these are reachable when no image slot is ever created in the first place.

## 2. Fix: real estate is now its own photo-led family
* `lib/premium/grounding.js`: new `family: 'realestate'` (was folded into `professional`). Own `RULES.realestate` (forbids menu/pricing/productShowcase sections and hospitality/SaaS words; CTA vocabulary contact/schedule/view/browse/search; **`primaryCTA: 'Contact an Agent'`**, never "Browse/View Listings"). `imagerySubjects`/`imageryAvoid` tuned for property/interior photography. `unsupportedFacts` extended with "current listings or active inventory", "specific building/market expertise claims", "neighbourhood sales statistics".
* `lib/premium/visuals.js`: new `PROFILES.realestate` — **`photoLed: true`**, `heroVariants: ['fullbleed-image','split','asymmetric-offset','editorial-rail']` (deliberately **excludes** every text-only layout), starter fallback `realestate-scene` (a city-skyline SVG, used only if a real photo request fails — never a random brand mark as the primary visual).
* `lib/premium/editorial.js`: `realestate` added to `PHOTO_LED_FAMILIES`; a real-estate shot list (hero, neighbourhood, buyer-lifestyle interior, seller-staged interior, architectural detail — 4 minimum); a `realestatePack()` (positioning, "Buying / Selling / Neighbourhoods" cards, a rotated **safe** offer label, buyer/seller/neutral FAQ, per-role process labels).

## 4. Truthfulness (Parts 5, 16, 17)
* Every real-estate image prompt is framed as **editorial/illustrative** ("a well-composed home exterior… no address or signage visible", "no people"); nothing in the prompt or the surrounding copy claims a specific address, a sold status or a named client.
* **New deterministic guard**: `sanitizeListingClaim()` scans every copy field; a phrase like *"current/active/available/our/exclusive listings"* or *"current inventory/properties"* is rewritten to a rotated, honest framing ("Areas we specialize in", "Property types we work with", "What we help buyers find", "Neighbourhoods we know well"). Verified: it does **not** touch "our listing process" or ordinary buy/sell copy.
* **Found and fixed the same bug at its actual source**: the base (non-AI-planned, always-on) category defaults for `realestate` — `category.cta`, the persistent nav CTA and the footer CTA — were literally `"View Listings"` / `"Browse Listings"`, and rendered on **every** real-estate site (screenshot evidence below) regardless of any premium flag. Changed to `"Contact an Agent"` in both `script.js` and its export twin `lib/site-render.js`; `pricing` added to the forbidden-sections list.
* New rubric category **`BUSINESS_TRUTHFULNESS`** (semantic + critic-facing).

## 6. Process/timeline collision (Part 12)
* **Real DOM measurement**, not a guess: `lib/premium/mobile-check.js` gained `measureProcessCollisions(siteEl, widths)` — clones the live site at **desktop (1300), tablet (820) and mobile (390)**, and checks real `getBoundingClientRect()` overlap between adjacent process steps and between each step's number/icon and its own label.
* **CSS root cause hardened regardless of the exact trigger**: `.process-flow-step` (and every other card/feature grid) had no `min-width:0`, so a grid item's default `min-width:auto` lets a long, unbreakable grounded label (now common since V6/V7 write real labels like "Define the search" instead of one-word generic ones) force the column wider than its `1fr` share and visually bleed into the next step. Added `min-width:0` + `overflow-wrap:anywhere` to the process grid and to every other card/feature grid that now carries longer generated copy.
* **New rubric category `VISUAL_COLLISIONS`**: a genuine collision (from the client measurement above) produces a defect mapped back to the specific `process` section (by DOM order on the active page) with repair `set_process_variant`, which switches that section to the **`alternating`** layout — already vertical by design, so it cannot collide again. Unit-tested end to end: defect → repair → `imageDisplayVariant` → rendered `data-variant="alternating"`.
